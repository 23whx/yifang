# 双设备局域网验收操作单（尚未执行）

准备于2026-09-30。用户已表示之后可提供第二台同一局域网手机/电脑；目前没有真实双设备结果。本操作单不是验收报告，也不代表已部署。

## 先准备，不急着建房

1. 把两台物理设备叫作A和B。A可以是电脑，B可以是手机。两个浏览器标签页不算两台设备。
2. 两台连同一个普通家庭/办公局域网。记录是否为访客Wi-Fi、是否有设备隔离；不要为了测试关闭整个防火墙或绕过证书警告。
3. 用户提供两台都能打开的**有效HTTPS**测试地址，并确认是包含最新修复的同一版本。当前`127.0.0.1:3000`只属于打开它的设备，不是B可访问的A地址。这里不启动公开监听、局域网开发监听、隧道或托管部署；部署仍由用户自行决定。
4. 浏览器允许本站在原标签页保存数据。保留已有对局，勿清理站点数据；新测试另开标签页。原标签页与新开的标签页不是同一个恢复存档。
5. 确定能私下交换完整文字的方式。手动模式的邀请/应答不是网址，不粘贴到浏览器地址栏；只发给测试同桌，不公开截图或粘贴完整连接码、网络地址、恢复凭证、存档。
6. A和B分别记录浏览器名称/版本、设备类别、页面语言与网址路径。无需提供公网IP、MAC地址或账户信息。
7. 至少一台用 iPhone 的 Safari。2026-10-11 已在同一台电脑的多个标签页自动验证：Chromium 上九种房间的连接与首个动作同步；Firefox 上除国标外的八种；手机模拟（iPhone 13、Pixel 7）上的国际象棋与日式立直；刷新恢复覆盖国际象棋（Chromium、Firefox）与三种麻将（Chromium），以及关页后的断线提示。扑克刷新恢复与围棋计分阶段的恢复未在浏览器中自动验证。Playwright 的 Windows 版 WebKit 没有 WebRTC，所以 Safari 只能真机验证。
8. 可选：在微信等应用内浏览器打开对战页。若该浏览器不支持 WebRTC，页面应在建房前直接提示“这个浏览器不支持网页直连（WebRTC）”并建议换用浏览器，而不是显示“无法加载规则”。记录实际提示原文。

缺少可访问的安全页面时，记录“环境未准备”，不尝试用普通HTTP局域网地址冒充通过。

## 第一轮：先中国象棋，两人即可

此轮只验中国象棋，不用一次同时建全部游戏的房间。A打开`/en/xiangqi/remote`，B打开`/zh/xiangqi/remote`，故意两种语言配对。

### 连接

1. 双方保持默认的邀请码方式（局域网直连）。不要展开“连接说明与常见问题”改选公共短房间码模式，否则不能算无信令的LAN测试。
2. A在“Open a room”卡片点击“Create invitation code”。等待邀请文字出现，将**全部文字**私下发给B。
3. B在“朋友邀请我”卡片粘到“粘贴房主发来的邀请码”，点“生成回复码”。把出现的完整应答私下发回A。
4. A粘到“Paste your friend’s reply code”，点“Connect with reply code”。只出现邀请码不算连接成功。
5. 双方都出现对应的“轮到你了/等待对方落子”或英文提示，才记建连通过。若报错，记录原文及发生步骤；不拿新房间覆盖已有存档反复尝试。

### 走棋同步

1. A点自己的一个兵，点向前一步的合法标记位置。没有标记就换一枚己方兵，不拖动浏览器页面来代替移动棋子。
2. B确认看到了相同棋子移动，并且变成自己走。B也移动一个卒向前一步。
3. 双方再各走一步，总共四步；每一步记录走前/走后轮次、两端棋子位置。等待方试点棋子不得提交新的走棋。
4. 截图只保留棋盘与状态，不含邀请/应答文本。棋盘可能因红黑视角旋转，不以“在屏幕左边还是右边”判断是否一致；对照坐标和棋子身份。

“网页打开”不是“连接通过”，“连接通过”也不是“游戏同步通过”。

### 刷新后恢复同一局

1. 四步后，先确认刷新前双方连接正常；刷新后应显示“发现本标签页保存的上次对局”或“This tab has a saved match”。记录棋盘、轮次与棋谱；不要导出存档。
2. **刷新原来的两个标签页**，不关闭标签页、不另开新标签页，不点击清除存档或确认新局。
3. 两端点“恢复上次对局 / Restore previous match”。原房主A会直接生成新的邀请码；原客方B在恢复模式粘贴邀请码，点“生成回复码”；A粘贴回复码并连接。
4. 等待验证完成。应回到原棋盘、原座位、原轮次和四步棋谱，不是重新排好32枚棋子；验证完成前不能走棋。
5. 轮到的一方再走一步，另一方确认同步。只有“旧局一致＋继续动作同步”都取得，才记恢复通过；仅新通道连通不够。
6. 恢复失败时保留双方原页及存档，记录错误。旧邀请码不能当作新的恢复邀请码；不可把“成功建立另一个新局”记成旧局恢复成功。

## 后续逐种验，不把一种通过推广到全部

每种都分别记录初次连接、至少数次双方动作、刷新恢复、恢复后续做。两人扑克另需完整一手结算/余额守恒及下一手；四人牌局记录原座位、各自手牌和当前步骤，不公开全桌私有牌。

| 围棋 | `/zh/go/remote`及英文对应页 | 2 | 落子、停一手、计分中的死子标记/双方确认与恢复 |

四人模式中，房主分别为玩家2/3/4生成不同邀请，回复粘回对应席位。恢复时每席保留自己的原页存档、先选择恢复；到齐后房主再点“继续原牌局”，不得点重新开局。

可以用A一席＋B三个独立标签页完成“两台设备、四逻辑席位”的初验，但必须如实标注；它不证明四台设备、四种浏览器或三条独立物理链路都通过。更多设备可用时再补，不能伪装为四设备验收。

## 真正断网另测，不与刷新混为一谈

前面成功后再约定短暂断网测试，先保留存档。仅由用户在测试设备上操作网络；不动整个路由器、不关闭防火墙、不影响其它人的工作。

记录断开/恢复的实际时间、页面状态、是否冻结、恢复后棋谱/牌局是否一致。有网线或移动数据备援时只关Wi-Fi未必断开实际链路。浏览器开发工具“离线”也未必阻断原生WebRTC。本项目同机试过离线6.5秒仍连接，因此不得用这个开关证明五秒断连宽限。

浏览器在手机后台可能暂停调度；“没有看到错误”不代表抖动恢复通过。未实际观察到连接断开/恢复，就记录场景未触发。长期断开后应保留原局，不以断线自动判对方获胜；重新连接需要原页存档与新的交换流程，不能保证手机进程被系统杀死后仍有最后一步存档。
